# Component Context: bp_contracts/ObjectRelationship

## Overview
This directory defines the **Rich Domain Models** that represent the actual business data (Products, Deals, Documents). These objects are complex aggregators that "know" how to format themselves for the frontend.

> **Deep Dive**: See [Object Traits](./traits/PROJECT_CONTEXT.md) for Entity Schemas (Capsules).

## Core Entities

### 1. `Contract.php` (The Aggregate Root)
**Role**: Represents a "Deal" or "Folder" that groups everything related to a customer transaction.
- **Attributes**: `serialNumber` (Unique ID), `nameContract` (Client Name), `status`.
- **Components**:
    - **`Dialogs`**: Collection of chat threads (`DialogConsultation`, `DialogOrder`).
    - **`Orders`**: Array of Product Orders (Kitchens/Wardrobes).
- **Key Logic**:
    - **Dynamic Access**: `checkWhoBlockedAccess()` handles "Blacklisting" or permission revocation.
    - **Lazy Loading**: Can load Orders/Dialogs on demand to optimize performance.

### 2. `Order.php` (The Product)
**Role**: A specific item being sold (e.g., "Kitchen Modern").
- **Sync**: Tightly coupled with the ERP status.
- **Data**: Contains technical specs (Facades, Colors, Dimensions) formatted for display.

### 3. `Invoice.php` & `Shipment.php` (Documents)
**Role**: Financial and Logistic records.
- **Workflow**:
    - Generated by Factory (Bookkeeper).
    - Visible to Dealer (as PDF download).
    - Status updates (Paid/Shipped) trigger notifications.

## Architecture Notes
- **Traits**: Heavy use of Traits (e.g., `CapsuleContract`) to share formatting logic between different entity types.
- **Serialization**: Method `getContractForCheck()` (and similar) prepares the array structure specifically for `json_encode` -> WebSocket transmission.
